# 环境搭建与容器部署

> 本文合并自「安装及编译」「容器发布」，按逻辑重组：开发机环境 → openpilot 编译
> → ARM64/Jetson 容器构建与发布 → JetPack 版本与升级 → Jetson 部署。

## 一、开发机环境（Ubuntu 24.04）

### 1. 安装 Docker（阿里云镜像源）

```bash
# 导入密钥
curl -fsSL https://mirrors.aliyun.com/docker-ce/linux/ubuntu/gpg | \
  sudo gpg --dearmor -o /etc/apt/keyrings/docker.gpg
sudo chmod a+r /etc/apt/keyrings/docker.gpg

# 配置国内源
echo "deb [arch=$(dpkg --print-architecture) signed-by=/etc/apt/keyrings/docker.gpg] \
  https://mirrors.aliyun.com/docker-ce/linux/ubuntu \
  $(. /etc/os-release && echo "$VERSION_CODENAME") stable" | \
  sudo tee /etc/apt/sources.list.d/docker.list > /dev/null

# 安装
sudo apt update
sudo apt install -y docker-ce docker-ce-cli containerd.io docker-buildx-plugin docker-compose-plugin
```

镜像加速器：
```bash
sudo mkdir -p /etc/docker
sudo tee /etc/docker/daemon.json <<-'EOF'
{
  "registry-mirrors": [
    "https://mirror.ccs.tencentyun.com",
    "https://hub-mirror.c.163.com",
    "https://docker.m.daocloud.io"
  ]
}
EOF
sudo systemctl daemon-reload && sudo systemctl restart docker && sudo systemctl enable docker
```

### 2. 安装 NVIDIA Container Toolkit（GPU 容器支持）

前置：确认已装 NVIDIA 驱动（`nvidia-smi`；无则 `sudo ubuntu-drivers install`）。

```bash
# 密钥与源
curl -fsSL https://nvidia.github.io/libnvidia-container/gpgkey | \
  sudo gpg --dearmor -o /usr/share/keyrings/nvidia-container-toolkit-keyring.gpg
curl -s -L https://nvidia.github.io/libnvidia-container/stable/deb/nvidia-container-toolkit.list | \
  sed 's#deb https://#deb [signed-by=/usr/share/keyrings/nvidia-container-toolkit-keyring.gpg] https://#g' | \
  sudo tee /etc/apt/sources.list.d/nvidia-container-toolkit.list

# 安装 + 配置 Docker 运行时
sudo apt-get update && sudo apt-get install -y nvidia-container-toolkit
sudo nvidia-ctk runtime configure --runtime=docker
sudo systemctl restart docker

# 验证
sudo docker run --rm --runtime=nvidia --gpus all nvidia/cuda:12.0.1-base-ubuntu22.04 nvidia-smi
```
> 若 `curl` 遇 `SSL_ERROR_SYSCALL`，多为 `nvidia.github.io` 访问受限，配代理或重试。

## 三、ARM64 / Jetson 容器构建与发布

构建流程：ARM 云主机（或 buildx）编译 → 镜像 → scp/pull 到 Jetson 运行（L4T + NVIDIA runtime）。

```bash
# 构建基础镜像与应用镜像
docker build --platform linux/arm64 -t openpilot-base-arm64 -f Dockerfile.openpilot_base .
docker build --platform linux/arm64 -t openpilot-arm64 -f Dockerfile.openpilot-arm64 .

# 本地调试运行（挂载源码 + ccache）
docker run -it --rm \
  -v /root/openpilot:/home/op/openpilot \
  -v ~/.ccache:/ccache \
  openpilot-arm64 bash
```

### raylib 依赖（UI 需要，aarch64 静态库）
```dockerfile
RUN apt-get update && apt-get install -y \
  build-essential g++ cmake git \
  libx11-dev libxrandr-dev libxinerama-dev libxcursor-dev libxi-dev libxext-dev \
  libxrender-dev libxfixes-dev libxkbcommon-dev libgl1-mesa-dev libegl1-mesa-dev \
  && rm -rf /var/lib/apt/lists/*

RUN git clone https://github.com/raysan5/raylib.git /tmp/raylib && \
    cd /tmp/raylib && git checkout 4.5.0 && \
    mkdir build && cd build && \
    cmake .. -DBUILD_SHARED_LIBS=OFF -DPLATFORM=Desktop && make -j$(nproc)

RUN mkdir -p third_party/raylib/aarch64/include && \
    cp /tmp/raylib/build/raylib/libraylib.a third_party/raylib/aarch64/ && \
    cp -r /tmp/raylib/src third_party/raylib/aarch64/include/raylib
```

### 发布与运行
```bash
docker tag openpilot-arm64:latest mindcont/openpilot-arm64:latest
docker push mindcont/openpilot-arm64:latest

docker run -it --rm --network host mindcont/openpilot-arm64:latest bash
```

已确认容器使用 NVIDIA runtime（`docker inspect openpilot-ui | grep Runtime` → `"Runtime": "nvidia"`），
Docker ↔ Jetson ↔ GPU 链路打通。

## 四、JetPack / Ubuntu 版本对照（2026-07 核对）

Jetson 端跑 L4T，Ubuntu 版本随 JetPack：

| JetPack | L4T | 设备端 Ubuntu | 内核 / CUDA | 备注 |
|---------|-----|--------------|-------------|------|
| 5.x | 35.x | 20.04 | 5.10 | 旧 |
| 6.x | 36.x | **22.04** | 5.15 / CUDA 12 | 生态成熟 |
| **7.0 / 7.2** | 38.2 / 39.2 | **24.04 LTS** | 6.8 / CUDA 13 | 最新，与本项目 24.04 对齐 |

- JetPack **7.2** 才把 24.04/CUDA 13 扩展到整个 **Jetson Orin** 系列 → Orin NX 可刷 24.04，
  与 `Dockerfile.openpilot-arm64`（基于 24.04）天然一致。
- 权衡：选 7.2 设备端与项目 24.04 一致，但生态很新、CUDA 13 需验证 tinygrad GPU 后端；
  选 6.2（22.04）生态成熟但与项目 24.04 有 glibc/依赖差异。openpilot 推理走自带 tinygrad，
  对 PyTorch wheel 依赖小。

### 6.x → 7.2 升级路径

**跨大版本不能 `apt upgrade`**（内核 5.15→6.8、bootloader/分区都变）。同大版本（6.2.1→6.2.2）
可改源 `apt full-upgrade` 原地升。前提：7.2 要求设备已有 6.x 代 UEFI/QSPI 固件。

| 方式 | 恢复模式 | host PC | 说明 |
|------|---------|--------|------|
| ① SDK Manager 重刷 | 需 RCM | 需(22.04/24.04) | 最常规，全量重刷清空设备 |
| ② ISO USB 安装器 | 否 | 否 | 7.2 新增，主要面向 devkit |
| ③ 镜像式 OTA | 否 | 否 | 原地升，**有 brick 案例，风险高** |

**推荐 ① SDK Manager 重刷**（当全新安装），生产设备勿用 ③ OTA。
> Orin NX 进 RCM 的针脚取决于载板，查 carrier 手册（一般短接 FC_REC + GND 再上电）。

升级前备份：
```bash
tar czf ~/orin_backup_$(date +%F).tar.gz \
  /data/params /data/media/0/realdata ~/openpilot/start_openpilot_orinnx.sh
rsync -avz orin:~/orin_backup_*.tar.gz ./
```

刷完 7.2 验证 checklist：
- [ ] tinygrad 用上 GPU（CUDA 13）：`DEV=CUDA` 跑 modeld 确认无 CPU fallback
- [ ] V4L2 双摄采集：`v4l2-ctl --list-devices`，单摄 `SINGLE_CAM=1` 跑通
- [ ] ARM64 容器在 24.04 + nvidia runtime 下能起
- [ ] manager 首次跑通（onboarding 由启动脚本跳过）
- [ ] 车道线出得来：订阅 `modelV2` 看 `laneLineProbs > 0.5`

## 五、Jetson 部署（systemd 开机自启）

`/etc/systemd/system/openpilot.service`：
```ini
[Unit]
Description=OpenPilot Docker (Jetson)
After=docker.service graphical.target
Requires=docker.service

[Service]
Restart=always
RestartSec=5
TimeoutStartSec=0
Environment=DISPLAY=:1
Environment=XDG_RUNTIME_DIR=/tmp/runtime-root
ExecStartPre=/usr/bin/xhost +local:docker
ExecStart=/usr/bin/docker run --rm --name openpilot \
  --network host --ipc host --runtime nvidia --privileged \
  -e DISPLAY=:1 -e XDG_RUNTIME_DIR=/tmp/runtime-root \
  -v /tmp/.X11-unix:/tmp/.X11-unix:rw \
  -v /run/dbus/system_bus_socket:/run/dbus/system_bus_socket \
  -v /etc/machine-id:/etc/machine-id:ro \
  -v /data:/data \
  --device /dev/dri --group-add video \
  mindcont/openpilot-arm64:latest \
  /home/batman/openpilot/selfdrive/ui/ui
ExecStop=/usr/bin/docker stop openpilot

[Install]
WantedBy=graphical.target
```

## 七、装车后测试（2026-07-10 下午）

### 摄像头曝光调优（已修复并写入启动脚本）

两个 USB 摄像头（Realtek `0bda:3035`，`video0`=road 近视野、`video2`=wide 宽视野）
默认 `auto_exposure=3`（光圈优先自动），在停车场顶棚强反光场景下严重过曝，画面发白、
车牌/车道线不可辨。

排查步骤：
```bash
v4l2-ctl --list-devices                          # 确认两个摄像头分别是 video0/video2
v4l2-ctl -d /dev/video0 --list-ctrls              # 查看支持的曝光控制项
v4l2-ctl -d /dev/video0 --set-ctrl=auto_exposure=1                    # 切手动模式
v4l2-ctl -d /dev/video0 --set-ctrl=exposure_time_absolute=8           # 实测调整
```

实测结果（阴天顶棚停车场）：
- **road (video0)**：`exposure_time_absolute=8`（0.8ms）— 对着更亮天空区域，需更低曝光
- **wide (video2)**：`exposure_time_absolute=40`（4ms）

已写入 `start_openpilot_orinnx.sh`（`set_camera_exposure()` 函数，启动时自动应用，
因为该设置不持久化，重启/断连会恢复默认）。同时修正 `WIDE_CAM` 设备号（实测是
`video2` 非最初假设的 `video1`）。commit `507573a86`。

摄像头分辨率/格式实测：两者最高 **1600×1200@30fps，仅支持 MJPG（压缩）**格式，
与脚本假设的 1928×1208 不完全一致，需注意 `camera.py` 对 MJPG 解码的兼容性
（OpenCV `cv2.VideoCapture` 通常能自动解码，未见异常）。

### demo.mp4 车道线验证（部分成功：链路通，推理速度不足）

用 `NO_UI=1 python3 run_laneline_demo.py` 验证，链路本身走通：
```
CL context ready; loading model
models loaded in 1.1s, modeld starting
vision stream set up, main_wide_camera: False, use_extra_client: False
connected main cam with buffer size: 3493536 (1928 x 1208)
PC mode: using default calibration transform
```
OpenCL(pocl)、模型加载、摄像头视觉流连接均正常，**没有崩溃**。但持续打印
`skipping model eval. Dropped N frames`，未能稳定产出 `modelV2`/`laneLineProbs`。

根因：CPU 推理约 233ms/帧（≈4.3fps），追不上视频源默认 20fps（甚至降到
`WEBCAM_FPS=2` 后丢帧显著减少，但仍未观察到稳定的 `modelV2` 输出）。

**GPU 加速尝试与发现**：
- `tinygrad.Device.DEFAULT` 在 Orin 上确认是 `CUDA`（非 CPU），理论上有 GPU 加速能力。
- 但 `selfdrive/modeld/modeld.py` 第 4 行硬编码 `os.environ['DEV'] = 'QCOM' if TICI else 'CPU'`，
  在 import tinygrad **之前**无条件覆盖 `DEV`，导致外部设置 `DEV=CUDA` 环境变量也无效。
  已修复为 `os.environ['DEV'] = os.environ.get('DEV', 'QCOM' if TICI else 'CPU')`（尊重外部
  预设值，不改变任何默认行为），已同步到 Orin，**未提交**（尚在验证）。
- 用 `tegrastats` 实测确认修复前 GPU 利用率 `GR3D_FREQ 0%`，CPU 某核心 60-98%，佐证
  确实全程走 CPU。
- 修复后设 `DEV=CUDA` 测试，modeld **崩溃**：
  ```
  tinygrad.engine.jit.JitError: args mismatch in JIT: ... 'CPU') != ... 'CUDA')
  ```
  原因：模型的 `.pkl` 预编译 JIT 缓存是按 CPU 设备的计算图序列化的，换后端后部分
  输入张量 device 标记不一致，JIT 缓存直接报错。**需要为 CUDA 后端重新生成/编译模型
  缓存才能解决，工作量超出本次范围，留作后续任务**。
- 结论：**当前 demo.mp4 只能在 CPU 模式下运行，且因推理速度不足暂未能验证到稳定的
  laneLineProbs 输出**；GPU 加速是后续解锁流畅车道线预测的关键路径。
  （后续进展：当晚继续排查，CUDA 后端本身验证可用、模型缓存重新编译成功且快 22 倍，
  但接入 modeld 多进程运行时后挂起，未解决，详见第八节）

### CAN 总线：Jetson 原生口失败 → panda 验证成功

**第一次尝试：Jetson 内置 CAN 控制器（`can0`，`mttcan` 驱动，Tegra 原生 CAN，非 panda）**
```bash
sudo ip link set can0 type can bitrate 500000
sudo ip link set can0 up
candump can0     # 监听 5 秒
```
结果：**0 包，0 错误，0 miss**。`berr-counter`/`bus-errors`/`error-warn` 全为 0，说明
不是接线极性反或速率错（那样会有错误计数），而是该总线口完全没有电气活动 ——
大概率是这个口没接线，或接的总线本身在休眠。**已确认此路径不可用，弃用。**

**第二次尝试：comma panda（USB，即"红熊猫"）**

`lsusb` 确认识别到 `ID 3801:ddcc comma.ai panda`（序列号
`3e001d001051313338343730`，固件 `DEV-3dd38b76-DEBUG`，对应 panda 子模块当前 commit
的自编译开发版）。

用 `panda` Python 库直接测试（`from panda import Panda; Panda.list()`）：
```python
p.health()
# {'voltage': 12661, 'ignition_line': 1, 'ignition_can': 0,
#  'car_harness_status': 2, ...}
```
- **voltage: 12.661V** — 车辆电瓶正常供电，harness 接线良好
- **ignition_line: 1** — 车辆当前点火状态（ACC 或以上）
- **car_harness_status: 2** — harness 已插入并被识别（具体型号待核对 panda 定义）
- **ignition_can: 0** — panda 尚未从 CAN 总线本身检测到点火唤醒帧（与下方大量收
  到消息的结果看似矛盾，可能是该字段判断逻辑与总线活跃度定义不同，需要后续确认）

设置 `set_safety_mode(CarParams.SafetyModel.allOutput)`（仅监听/透传，不做控制）后，
`can_recv()` 监听 5 秒：
```
共收到 21454 条 CAN 消息  (~4290 msg/s)
涉及总线: [0, 1, 2]        # 三条总线均有数据
不同 CAN ID 数量: 176
```
**结论：panda 是正确的 CAN 接入方式**（openpilot 架构本身通过 `pandad` 走 panda，
不是走 socketCAN），已确认能稳定收到大量真实车辆 CAN 数据，三条总线（可能是
Powertrain / Comfort / Gateway 诊断口等）均有信号。

**API 使用注意**（供后续参考，避免重复踩坑）：
- `Panda.can_recv()` 返回值是 `(address, dat, bus)` **三元组**，不是四元组。
- 安全模式常量不在 `Panda` 类上（`Panda.SAFETY_ALLOUTPUT` 不存在），要用
  `from opendbc.car.structs import CarParams` 的 `CarParams.SafetyModel.allOutput`。
- 通过 SSH 传多行 Python/Bash（heredoc、`python3 -c "多行"`）经常被吞掉换行导致
  `IndentationError`，稳定做法是本地写脚本文件再 `scp` 过去执行。

## 八、GPU 推理专项调试（2026-07-10 晚，进行中）

### 结论先说：GPU 硬件/驱动/CUDA 后端可用，卡点收窄到 modeld 多进程集成

**不应再笼统地说"GPU 参与推理是核心难点"**——已有确凿证据表明 tinygrad 的 CUDA
后端在 Orin NX 上完全可用，且编译出的 CUDA 版本模型缓存单独测试速度和正确性都通过。
真正未解决的是一个更具体的问题：**把 CUDA 推理接入 `modeld` 的多进程运行时后挂起**，
需要独立的一轮调试，不是"GPU 用不了"这种根基性问题。

### 第一步：验证 tinygrad CUDA 后端本身是否可用 —— 通过

最小复现（不涉及 openpilot 模型，纯 tinygrad 算子）：
```python
import os
os.environ['DEV'] = 'CUDA'
from tinygrad import Tensor, Device
a, b = Tensor.randn(1024, 1024), Tensor.randn(1024, 1024)
c = (a @ b).realize()
print(c.device, c.sum().numpy())
```
结果：`Device.DEFAULT: CUDA`，矩阵乘法在 GPU 上跑通，数值正确。**证明 CUDA 驱动、
nvrtc、nvJitLink、tinygrad CUDA 后端全部就位可用**，此前"崩溃"的原因不在这一层。

### 第二步：重新编译 CUDA 版本的模型缓存 —— 编译成功，速度提升 ~22 倍

官方 `tinygrad_repo/examples/openpilot/compile3.py` 就是生成 `driving_vision_tinygrad.pkl`
/`driving_policy_tinygrad.pkl` 的源脚本（不是黑盒产物），可以指定 `DEV=CUDA` 重新编译：
```bash
cd ~/openpilot
DEV=CUDA python3 tinygrad_repo/examples/openpilot/compile3.py \
  selfdrive/modeld/models/driving_vision.onnx /tmp/driving_vision_cuda.pkl
```

**踩坑：CUDA Graph 优化路径有 bug**，直接跑会在 JIT 捕获阶段崩溃：
```
tinygrad/runtime/graph/cuda.py:32: kern_params = cuda.CUDA_KERNEL_NODE_PARAMS_v1(ji.prg._prg.prg, ...)
TypeError: expected c_void_p instead of NoneType
```
`JIT_BATCH_SIZE=0`（默认值）不能禁用 CUDA Graph，只是不限制批大小。tinygrad 也没有现成
的环境变量能整体关闭 Graph。**规避方式**：猴子补丁，在 `CUDADevice.__init__` 执行后把
`self.graph` 设为 `None`：
```python
import tinygrad.runtime.ops_cuda as ops_cuda
_orig_init = ops_cuda.CUDADevice.__init__
def _patched_init(self, device):
    _orig_init(self, device)
    self.graph = None  # 禁用 CUDA Graph，规避已知 bug
ops_cuda.CUDADevice.__init__ = _patched_init
```
补丁后编译成功：
```
**** compile done ****
enqueue   9.5 ms -- total run  10.5 ms   # 对比 CPU 233ms/帧，约 22 倍提升
```
`jit run validated` 自检通过。`driving_policy` 编译时脚本自带的
`test_vs_compile`（"输入乘 2 应导致输出变化"）报了 `AssertionError not raised`，但这只是
该自检对 policy 模型输入结构（大量 one-hot/缓冲区）不适用的假警告——单独验证 pkl 能
正常 `pickle.load` 并还原成有效的 `TinyJit` 对象，编译产物本身没问题。

### 第三步：接入 modeld 真实运行时 —— 挂起，未解决

把 CUDA 版 pkl 换上、用同样的猴子补丁包一层去启动 `run_laneline_demo.py`：
- **没有报错，也没有崩溃**
- `modeld` 子进程持续占 65-72% CPU，但 **60+ 秒内 0 次 `modelV2` 输出**
- 内存持续增长（2.4GB → 2.9GB，无收敛），怀疑存在资源泄漏
- `/proc/<pid>/fd` 下**没有** `/dev/nvidia*`/`/dev/nvhost*`，说明 CUDA 设备可能没被
  真正打开

**怀疑根因（未证实）**：`modeld` 是 `multiprocessing.Process`（Linux 默认 `fork`）启动的
子进程，猴子补丁是在**父进程**里对 `CUDADevice.__init__` 打的。CUDA context 是出了名的
"fork 不安全"资源——如果父进程在 fork 前已经出于某种原因触碰过 CUDA（哪怕只是 import
阶段的懒加载），子进程继承的 context 可能是无效的，导致后续 CUDA 调用挂起而不报错。
`tinygrad/engine/realize.py` 里 `CompiledRunner.__reduce__` 的设计（序列化时只存
`ProgramSpec`，反序列化时重新调用 `Device[...].runtime()`）本身是对跨进程场景友好的，
但这依赖 `Device[p.device]`（`CUDADevice` 单例）在当前进程里处于正确状态，猴子补丁的
fork 时序可能破坏了这个前提。

此外，`modeld` 同一进程内还并行使用 OpenCL（pocl，做图像预处理）和 CUDA（tinygrad
推理）两套 GPU/计算后端，两者在 fork 出的子进程里的初始化顺序也是潜在的冲突点。

**没有继续深挖的原因**：已经在这个具体问题上调整两次（关 CUDA Graph、修
`__file__` 未定义），第三次改动前选择停下来记录现状而不是继续小修小补——这类
"无报错但挂起"的问题最有效的排查方式是拿到真实调用栈（`py-spy dump`，Orin 上未安装），
而不是继续猜测性打补丁。

**已回滚**：`driving_vision_tinygrad.pkl`/`driving_policy_tinygrad.pkl` 已从
`/tmp/pkl_cpu_backup/` 恢复为原始 CPU 版本，系统保持在已验证可用的 CPU 推理状态。
pkl 文件本身在 `.gitignore` 中不受版本控制，此次操作不影响仓库状态。

### 后续排查建议（下次接手时的起点）

1. 先装 `py-spy`（`pip install py-spy` 或 `apt install`），能在不重启进程的情况下
   `py-spy dump --pid <modeld_pid>` 拿到 Python 调用栈，直接定位卡在哪一行。
2. 排除 fork 时序变量：不用猴子补丁包装脚本，直接改 `selfdrive/modeld/modeld.py`
   或 `tinygrad_repo/tinygrad/runtime/ops_cuda.py` 源码一行（`self.graph = None`），
   走正常的 `DEV=CUDA ./start_openpilot_orinnx.sh` 启动路径，确认问题是否复现——如果
   直接改源码就不挂起，说明确实是猴子补丁 + fork 时序的问题；如果依然挂起，说明是
   OpenCL/CUDA 共存或别的更深层问题。
3. 检查 `/dev/nvidia*` fd 缺失是否是问题本身还是结果：可以在猴子补丁里加日志确认
   `CUDADevice.__init__` 是否真的在子进程里被再次调用过。
4. 备选方案：如果 CUDA + fork 的坑短期内解决不了，考虑 `multiprocessing` 显式设置
   `start_method='spawn'`（避免继承父进程状态，但需要评估对 manager 现有架构的影响
   范围，属于更大改动，谨慎评估）。
