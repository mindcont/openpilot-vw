# 环境搭建与容器部署

> 本文合并自「安装及编译」「容器发布」，按逻辑重组：开发机环境 → openpilot 编译
> → ARM64/Jetson 容器构建与发布 → JetPack 版本与升级 → Jetson 部署。

## 一、开发机环境（Ubuntu 24.04）

### 1. 安装 Docker（阿里云镜像源）

```bash
# 导入密钥
curl -fsSL https://mirrors.aliyun.com/docker-ce/linux/ubuntu/gpg | \
  sudo gpg --dearmor -o /etc/apt/keyrings/docker.gpg
sudo chmod a+r /etc/apt/keyrings/docker.gpg

# 配置国内源
echo "deb [arch=$(dpkg --print-architecture) signed-by=/etc/apt/keyrings/docker.gpg] \
  https://mirrors.aliyun.com/docker-ce/linux/ubuntu \
  $(. /etc/os-release && echo "$VERSION_CODENAME") stable" | \
  sudo tee /etc/apt/sources.list.d/docker.list > /dev/null

# 安装
sudo apt update
sudo apt install -y docker-ce docker-ce-cli containerd.io docker-buildx-plugin docker-compose-plugin
```

镜像加速器：
```bash
sudo mkdir -p /etc/docker
sudo tee /etc/docker/daemon.json <<-'EOF'
{
  "registry-mirrors": [
    "https://mirror.ccs.tencentyun.com",
    "https://hub-mirror.c.163.com",
    "https://docker.m.daocloud.io"
  ]
}
EOF
sudo systemctl daemon-reload && sudo systemctl restart docker && sudo systemctl enable docker
```

### 2. 安装 NVIDIA Container Toolkit（GPU 容器支持）

前置：确认已装 NVIDIA 驱动（`nvidia-smi`；无则 `sudo ubuntu-drivers install`）。

```bash
# 密钥与源
curl -fsSL https://nvidia.github.io/libnvidia-container/gpgkey | \
  sudo gpg --dearmor -o /usr/share/keyrings/nvidia-container-toolkit-keyring.gpg
curl -s -L https://nvidia.github.io/libnvidia-container/stable/deb/nvidia-container-toolkit.list | \
  sed 's#deb https://#deb [signed-by=/usr/share/keyrings/nvidia-container-toolkit-keyring.gpg] https://#g' | \
  sudo tee /etc/apt/sources.list.d/nvidia-container-toolkit.list

# 安装 + 配置 Docker 运行时
sudo apt-get update && sudo apt-get install -y nvidia-container-toolkit
sudo nvidia-ctk runtime configure --runtime=docker
sudo systemctl restart docker

# 验证
sudo docker run --rm --runtime=nvidia --gpus all nvidia/cuda:12.0.1-base-ubuntu22.04 nvidia-smi
```
> 若 `curl` 遇 `SSL_ERROR_SYSCALL`，多为 `nvidia.github.io` 访问受限，配代理或重试。

## 三、ARM64 / Jetson 容器构建与发布

构建流程：ARM 云主机（或 buildx）编译 → 镜像 → scp/pull 到 Jetson 运行（L4T + NVIDIA runtime）。

```bash
# 构建基础镜像与应用镜像
docker build --platform linux/arm64 -t openpilot-base-arm64 -f Dockerfile.openpilot_base .
docker build --platform linux/arm64 -t openpilot-arm64 -f Dockerfile.openpilot-arm64 .

# 本地调试运行（挂载源码 + ccache）
docker run -it --rm \
  -v /root/openpilot:/home/op/openpilot \
  -v ~/.ccache:/ccache \
  openpilot-arm64 bash
```

### raylib 依赖（UI 需要，aarch64 静态库）
```dockerfile
RUN apt-get update && apt-get install -y \
```

## 四、JetPack / Ubuntu 版本对照（2026-07 核对）

Jetson 端跑 L4T，Ubuntu 版本随 JetPack：

| JetPack | L4T | 设备端 Ubuntu | 内核 / CUDA | 备注 |
|---------|-----|--------------|-------------|------|
| 5.x | 35.x | 20.04 | 5.10 | 旧 |
| 6.x | 36.x | **22.04** | 5.15 / CUDA 12 | 生态成熟 |
| **7.0 / 7.2** | 38.2 / 39.2 | **24.04 LTS** | 6.8 / CUDA 13 | 最新，与本项目 24.04 对齐 |

- JetPack **7.2** 才把 24.04/CUDA 13 扩展到整个 **Jetson Orin** 系列 → Orin NX 可刷 24.04，
  与 `Dockerfile.openpilot-arm64`（基于 24.04）天然一致。
- 权衡：选 7.2 设备端与项目 24.04 一致，但生态很新、CUDA 13 需验证 tinygrad GPU 后端；
  选 6.2（22.04）生态成熟但与项目 24.04 有 glibc/依赖差异。openpilot 推理走自带 tinygrad，
  对 PyTorch wheel 依赖小。

### 6.x → 7.2 升级路径

**跨大版本不能 `apt upgrade`**（内核 5.15→6.8、bootloader/分区都变）。同大版本（6.2.1→6.2.2）
可改源 `apt full-upgrade` 原地升。前提：7.2 要求设备已有 6.x 代 UEFI/QSPI 固件。

| 方式 | 恢复模式 | host PC | 说明 |
|------|---------|--------|------|
| ① SDK Manager 重刷 | 需 RCM | 需(22.04/24.04) | 最常规，全量重刷清空设备 |
| ② ISO USB 安装器 | 否 | 否 | 7.2 新增，主要面向 devkit |
| ③ 镜像式 OTA | 否 | 否 | 原地升，**有 brick 案例，风险高** |

**推荐 ① SDK Manager 重刷**（当全新安装），生产设备勿用 ③ OTA。
> Orin NX 进 RCM 的针脚取决于载板，查 carrier 手册（一般短接 FC_REC + GND 再上电）。

升级前备份：
```bash
tar czf ~/orin_backup_$(date +%F).tar.gz \
  /data/params /data/media/0/realdata ~/openpilot/start_openpilot_orinnx.sh
rsync -avz orin:~/orin_backup_*.tar.gz ./
```

刷完 7.2 验证 checklist：
- [ ] tinygrad 用上 GPU（CUDA 13）：`DEV=CUDA` 跑 modeld 确认无 CPU fallback
- [ ] V4L2 双摄采集：`v4l2-ctl --list-devices`，单摄 `SINGLE_CAM=1` 跑通
- [ ] ARM64 容器在 24.04 + nvidia runtime 下能起
- [ ] manager 首次跑通（onboarding 由启动脚本跳过）
- [ ] 车道线出得来：订阅 `modelV2` 看 `laneLineProbs > 0.5`

## 七、装车后测试（2026-07-10 下午）

### 摄像头曝光调优（已修复并写入启动脚本）

两个 USB 摄像头（Realtek `0bda:3035`，`video0`=road 近视野、`video2`=wide 宽视野）
默认 `auto_exposure=3`（光圈优先自动），在停车场顶棚强反光场景下严重过曝，画面发白、
车牌/车道线不可辨。

排查步骤：
```bash
v4l2-ctl --list-devices                          # 确认两个摄像头分别是 video0/video2
v4l2-ctl -d /dev/video0 --list-ctrls              # 查看支持的曝光控制项
v4l2-ctl -d /dev/video0 --set-ctrl=auto_exposure=1                    # 切手动模式
v4l2-ctl -d /dev/video0 --set-ctrl=exposure_time_absolute=8           # 实测调整
```

实测结果（阴天顶棚停车场）：
- **road (video0)**：`exposure_time_absolute=8`（0.8ms）— 对着更亮天空区域，需更低曝光
- **wide (video2)**：`exposure_time_absolute=40`（4ms）

已写入 `start_openpilot_orinnx.sh`（`set_camera_exposure()` 函数，启动时自动应用，
因为该设置不持久化，重启/断连会恢复默认）。同时修正 `WIDE_CAM` 设备号（实测是
`video2` 非最初假设的 `video1`）。commit `507573a86`。

### 曝光问题的根本矛盾与软件自动曝光方案（2026-07-10）

**发现**：固定曝光值只适配单一光照场景，实测三种场景需要三组完全不同的值：
- 阴天顶棚停车场(强反光)：road exposure=8, wide exposure=40
- 室内/车内看真实道路(常光)：road/wide exposure=50 gain=40
- 曾误设 exposure=300 gain=128：室内场景下严重过曝发白

早中晚/室内外光照差异很大，靠启动时写死一组值不可持续，需要运行时自适应。

**调研：官方 openpilot 怎么处理**（`system/camerad/cameras/camera_qcom2.cc` +
`camera_common.cc`）：在真实传感器(AR0231/OX03C10/OS04C10)上跑逐帧闭环自动曝光——
在按摄像头焦距换算出的 ROI 内测中位灰度，与随场景动态调整的目标灰度比较，用两个
时间常数不同的低通滤波（灰度环 `ts_grey=10s` 防抖，EV 环 `ts_ev=0.05s` 跟手）算出
期望 EV，再在增益表中搜索最优 `(exposure_time, gain)` 组合，通过 I2C 直接写传感器
寄存器。这套算法深度绑定 comma 专用传感器的寄存器/增益表，USB webcam 走标准 V4L2/
UVC 接口，没有这个通道，**不能直接搬用**，但"测光 ROI + 动态目标灰度 + 双时间常数
平滑反馈环"的控制思路值得借鉴。

**调研：社区/行业方案**：V4L2 驱动内建的连续自动曝光（`auto_exposure=3`）在大多数
UVC 设备上可用，但社区反馈其调节目标不透明、有时会覆盖手动设的值，且本项目已在
强反光停车场实测过这个默认模式严重过曝（本节起因）——不打算重新依赖它。机器人视觉
领域（如 [MIT-Bilab/vo-autoexpose](https://github.com/MIT-Bilab/vo-autoexpose)）
也认为通用摄像头固件自动曝光是为"人眼观感"优化，不是为视觉算法的检测目标优化，
这与官方 openpilot 自己实现测光环、不依赖传感器固件自动曝光的取向一致。OpenCV 的
`CAP_PROP_EXPOSURE` 在 V4L2 backend 下被多次报告不可靠，业界惯例是绕开 OpenCV、
直接用 `v4l2-ctl`/ioctl 控制。

**采用方案：软件闭环自动曝光**（`tools/webcam/auto_exposure.py`，默认关闭，
`AUTO_EXPOSURE=1` 启用）。设计要点：
- 测光：每帧对画面下半部分（道路 ROI，排除天空/引擎盖）取灰度均值，成本低
- 控制频率低（默认 1Hz）：曝光是慢变量，不需要逐帧调节，避免和 20fps 采集主循环
  抢时间、也避免震荡
- 双层调节：优先调 `exposure_time`（对画质影响更小），触及上下限后才调 `gain`
  （增益越高噪点越明显，做兜底而非首选）
- 一阶低通滤波平滑 + 死区（差值 <6% 不调节），防止画面明暗抽动
- 通过 `v4l2-ctl` 子进程写入（不用 `cv2.CAP_PROP_EXPOSURE`，理由见上）
- 安全范围：`exposure_time_absolute` 钳制在 5~450（450→45ms，20fps 帧周期 50ms
  留余量），`gain` 钳制在 0~128

**离线验证**（未接真实摄像头，模拟"亮度∝exposure×√gain"物理近似）：两个极端场景
（模拟"exposure=300,gain=128 用到暗场景"的严重过曝、"exposure=8,gain=64 用到暗
场景"的严重过暗）均在约 20 次迭代（≈20 秒）内收敛到目标灰度附近，无发散/震荡。
**实机（真实摄像头 + 真实光照变化）验证仍待做**，建议先手动模式验证链路正常，再开
`AUTO_EXPOSURE=1` 观察收敛效果，必要时调 `AE_TARGET_GREY`/`AE_INTERVAL`/
`AE_SMOOTH_ALPHA`（均为环境变量，见 `auto_exposure.py`）。

摄像头分辨率/格式实测：两者最高 **1600×1200@30fps，仅支持 MJPG（压缩）**格式，
与脚本假设的 1928×1208 不完全一致，需注意 `camera.py` 对 MJPG 解码的兼容性
（OpenCV `cv2.VideoCapture` 通常能自动解码，未见异常）。

### 第二步：重新编译 CUDA 版本的模型缓存 —— 编译成功，速度提升 ~22 倍

官方 `tinygrad_repo/examples/openpilot/compile3.py` 就是生成 `driving_vision_tinygrad.pkl`

**踩坑：CUDA Graph 优化路径有 bug**，直接跑会在 JIT 捕获阶段崩溃：

```python
def _patched_init(self, device):
    _orig_init(self, device)
    self.graph = None  # 禁用 CUDA Graph，规避已知 bug
ops_cuda.CUDADevice.__init__ = _patched_init
```

fork 时序可能破坏了这个前提。

此外，`modeld` 同一进程内还并行使用 OpenCL（pocl，做图像预处理）和 CUDA（tinygrad
推理）两套 GPU/计算后端，两者在 fork 出的子进程里的初始化顺序也是潜在的冲突点。

## 九、py-spy 定位真实根因（2026-07-10 深夜）—— 不是挂起，是逐帧重新调度导致的性能悬崖

### 结论：找到了确凿、可复现、有代码依据的根因，且修复方向明确

上一节的"挂起"判断是错的。用 `py-spy dump` 拿到真实调用栈后，证据表明进程**一直在
计算，只是极慢**，且慢的原因是架构层面的、一行代码可以解释清楚的性能问题，不是
"CUDA + fork 不安全"这种模糊的怀疑。

### 排查过程

**背景搜索**：搜索开源项目发现 `xnxpilot`（Jetson Xavier NX 上跑 openpilot 的项目），
虽然它用的是骁龙 QCOM/OpenCL `GPU` 后端而非 CUDA，但引出两个关键信息：
- tinygrad 官方文档记录 `JIT=2` 即"graphs disabled"，是内置、官方支持的禁用 JIT Graph
  方式，比之前用的猴子补丁更干净。本项目 `tinygrad_repo` 版本确认支持：
  `tinygrad/engine/jit.py:227` `if JIT < 2: apply_graph_to_jit(...)`。
- 用 `DEV=CUDA JIT=2`（不用任何猴子补丁）重新跑 `compile3.py` 编译两个模型，**编译
  成功，速度与猴子补丁方案一致**（~10.5ms/帧 vision，~3.7ms/帧 policy），证明官方方式
  同样能规避昨晚那个 CUDA Graph bug。

**用 `py-spy` 抓真实调用栈**：装上 `pip install py-spy --break-system-packages`（venv
里没有传统 pip，走系统 pip 装到用户目录）。对挂起中的 `modeld` 进程
`sudo py-spy dump --pid <pid>` 两次，间隔约 30 秒：

第一次：
```
run (selfdrive/modeld/modeld.py:202)
  realize (tinygrad/tensor.py:266)
  schedule_with_vars (tinygrad/tensor.py:253)
  _apply_map_to_tensors (tinygrad/tensor.py:32)
  topovisit (tinygrad/uop/ops.py:180)
```
第二次（30 秒后，同一行，内部子调用不同）：
```
run (selfdrive/modeld/modeld.py:202)
  realize (tinygrad/tensor.py:266)
  schedule_with_vars (tinygrad/tensor.py:253)
  _apply_map_to_tensors (tinygrad/tensor.py:36)
  substitute (tinygrad/uop/ops.py:347)
  graph_rewrite (tinygrad/uop/ops.py:1265)
```
两次都卡在 `modeld.py:202`，线程状态 `active+gil`（真的在跑，不是阻塞等待），但内部
经过的子函数不同——**说明它在推进，只是这一行代码的调度/图重写开销大到数十秒级**。
之后再抓一次，进程已推进到 `modeld.py:310`（主循环等下一帧），状态 `idle`——**第一帧
确实处理完了**，但为时已晚，`camerad` 早已把后续帧覆盖丢弃，导致 demo 脚本始终没能
凑够 40 帧去打印结果。第三次抓栈又回到同样的 `topovisit`/`graph_rewrite` 路径，证明
**每一帧都要重新付出这个高昂的调度代价**，不是一次性的冷启动开销。

### 根因：`modeld.py:202` 的 PC/非 TICI 路径每帧重建 Tensor 并调度

```python
if TICI and not USBGPU:
  # The imgs tensors are backed by opencl memory, only need init once
  for key in imgs_cl:
    if key not in self.vision_inputs:
      self.vision_inputs[key] = qcom_tensor_from_opencl_address(imgs_cl[key].mem_address, self.vision_input_shapes[key], dtype=dtypes.uint8)
else:
  for key in imgs_cl:
    frame_input = self.frames[key].buffer_from_cl(imgs_cl[key]).reshape(self.vision_input_shapes[key])
    self.vision_inputs[key] = Tensor(frame_input, dtype=dtypes.uint8).realize()  # <- modeld.py:202，卡点
```

- **TICI（comma 官方硬件）分支**：`if key not in self.vision_inputs`——**只初始化一次**，
  `qcom_tensor_from_opencl_address` 是零拷贝内存包装，之后每帧只是更新同一块内存的
  数据，Tensor 对象本身不重建，没有重复调度开销。
- **else（PC/本项目走的路径）**：**每一帧无条件**执行 `Tensor(...).realize()`，重新
  创建 Tensor 并立即触发调度。这行代码本身**没有被 JIT 包裹**（只有 `vision_run`/
  `policy_run` 两个大模型推理是 JIT 化的），纯靠 tinygrad 常规调度路径执行。
- 在 CPU/OpenCL 后端上，这行小操作的调度开销小到可忽略；但 CUDA 后端的
  `graph_rewrite`/调度路径对这种"每帧重新构建计算图"模式有严重性能劣化，且伴随
  内存持续增长（怀疑重建的计算图对象未被复用/释放）。

**这不是"CUDA 参与推理的核心难点"，是一个具体、有代码行号、有架构对比依据的性能
问题**：comma 官方硬件路径早就用"只初始化一次 + 零拷贝更新"绕开了这个代价，PC 路径
从未针对 CUDA 后端做类似优化（大概率因为 comma 官方从没在 CUDA 后端上跑过这条路径，
PC 模式设计初衷是 CPU/调试用，没考虑过 CUDA 场景下这行代码的性能）。

### 修复方向（已定位，尚未实施，需谨慎验证）

参照 TICI 分支的思路：让 CUDA 路径下的 `vision_inputs`/`policy_inputs` 也只做一次
Tensor 包装和分配，之后每帧只更新底层 buffer 数据，而不是重新 `Tensor(...).realize()`。
可能的方向（需要进一步验证细节，非最终方案）：
- 用 `.assign()` 或原地写入的方式复用已 realize 的 Tensor，而不是重新构造
- 或者判断 `Device.DEFAULT == 'CUDA'` 时也走类似"只初始化一次"的分支（类似 TICI
  分支的 `if key not in self.vision_inputs` 判断），用 CUDA 的零拷贝/固定内存机制

### 补充：联网搜索交叉验证（2026-07-10）

针对第十一节的排查方向，联网搜索找到两条有价值的外部依据：

**1. tinygrad 官方文档印证了"每帧重建 Tensor 触发调度"这个代价是机制性的，不是偶发 bug**

[tinygrad JIT 内部机制说明](https://mesozoic-egg.github.io/tinygrad-notes/20240102_jit.html)
指出 GPU 代码执行分两个阶段：① 源码编译成字节码——按 UOp 的 `ast.key` 走
`method_cache`，天然跨调用复用；② 字节码转成可执行的 compute graph/pipeline——**这一步
默认逐次重复**，只有显式用 `TinyJit` 包裹、进入其 batched/graph 模式后才会复用整个
pipeline，而不仅仅是复用编译产物。

这与本项目 `modeld.py:202` 的 `Tensor(frame_input, dtype=uint8).realize()` **没有被
TinyJit 包裹**这一事实完全对应：每帧都要重走 `schedule_with_vars → graph_rewrite →
topovisit` 这条"图构建"路径。CPU 后端这个开销小到可忽略，CUDA 后端的设备分发/kernel
选择元数据更重，同样的调度逻辑被放大成了可观测的性能瓶尖。这也解释了 comma 官方为什么
在 TICI 分支专门加了 `if key not in self.vision_inputs` 短路判断只做一次初始化——
他们显然也踩过这个坑。**第九节判断的方向得到官方机制文档的印证，可信度上升。**

**2. comma 工程师本人在 tinygrad 仓库报告过 openpilot 模型 JIT 集成问题**

[tinygrad/tinygrad#16335](https://github.com/tinygrad/tinygrad/issues/16335)（QCOM 后端，
`AssertionError: END src[0] should be KERNEL, not Ops.STORE`）虽然报的是不同后端、不同
断言错误，但证明 **openpilot 模型在较新 tinygrad 上的 JIT 集成本身官方也仍在踩坑**，
不是本项目环境独有的问题。后续若按 TICI 思路给 CUDA 路径做一次性初始化 + JIT 包裹，
遇到类似的图重写/JIT 断言错误不算意外，可参考该 issue 的复现脚本和排查方式。

**未找到直接支持的方向**：第八节"CUDA context 跨 fork 不安全"的怀疑，搜索未找到
tinygrad/CUDA 生态中的直接对应证据，结合本次 py-spy 采样已确认 CUDA fd 存在且至少
成功执行过一次推理，**建议放弃这个怀疑方向**。内存单调增长现象搜索只找到 PyTorch/CUDA
generic caching allocator 碎片化的通用讨论，与本项目现象类型相似但非同一框架，不能直接
作为证据，维持"需独立定量测量增长曲线"的待办。

### 修复方向优先级（结合搜索结果更新）

1. **优先**：给 CUDA 路径实现类似 TICI 分支的一次性初始化 + buffer 原地更新，避免
   `modeld.py:202` 每帧重新触发 `Tensor(...).realize()` 的调度开销。这是当前唯一有
   机制性文档 + 官方代码先例双重支持的方向。
2. 实施时预期可能遇到 JIT/图重写相关的断言错误（参考 #16335 的错误类型和排查方式），
   属于已知的同类坑，不代表方向错误。
3. 内存增长曲线仍需独立定量测量后才能判断是否是同一根因的另一表现，还是叠加的
   第二个问题，不要基于搜索结果直接假设是"caching allocator 碎片化"就下结论。

第七节记录的现象是：CPU 推理约 233ms/帧（≈4.3fps），默认 `WEBCAM_FPS=5`，持续打印
`skipping model eval. Dropped 1 frames`，当时判断为"未能验证到稳定的 laneLineProbs
输出"。本节在 hal9000（Orin NX）上用已恢复的 CPU 版 pkl 重新实测，找到了真正原因并验证
修复。

### 根因：`prepare_only` 追帧机制 + 输入帧率高于 CPU 处理能力，永远追不上

`selfdrive/modeld/modeld.py` 主循环逻辑：
```python
vipc_dropped_frames = max(0, meta_main.frame_id - last_vipc_frame_id - 1)
...
prepare_only = vipc_dropped_frames > 0
if prepare_only:
    cloudlog.error(f"skipping model eval. Dropped {vipc_dropped_frames} frames")
...
model_output = model.run(bufs, transforms, inputs, prepare_only)  # prepare_only=True 时不真正推理，model_output=None
```
这是一种防止越落后越多的"追帧"保护机制：一旦检测到已经落后于摄像头帧，这一帧就只准备
输入 buffer、不做真正推理，`model_output` 为 `None`，自然不产出 `modelV2`。

问题在于：CPU 推理速度（~4.3fps）天然低于默认 `WEBCAM_FPS=5`。只要输入速率持续高于
处理能力，**每一帧都会触发这个保护机制，永远不可能追上**，会一直打印
`Dropped 1 frames` 打印到天荒地老——这不是卡死、不是故障，是参数搭配问题。

用 py-spy 交叉验证：CPU 模式下抓栈能看到后台线程 `tinygrad/runtime/ops_cpu.py`
的 `_exec`/`run` 处于真实计算状态（`active`），主线程在 `_copyout`/`synchronize`
正常同步等待结果——**确认是在正常算，只是算得比来帧速度慢**，与 CUDA 模式下卡在
`topovisit`/`graph_rewrite`（纯调度开销）的性质完全不同。

### 验证：把 WEBCAM_FPS 降到 CPU 处理能力以下，立即稳定出结果

固定其他参数不变，只把 `WEBCAM_FPS` 从默认 5 降到 3（低于 CPU ~4.3fps 的处理能力）：
```bash
WEBCAM_FPS=3 NO_UI=1 python3 run_laneline_demo.py
```
效果：
- 启动后只有开头一次热身丢帧（`Dropped 3 frames`），之后再无新的丢帧打印
- py-spy 抓栈显示主线程 `idle`（在等下一帧到达，不是忙于计算）——证明处理能力已经
  富余，能跟上输入节奏
- 另开进程订阅 `modelV2` 实测：**15 秒内稳定收到 45 帧**，`laneLineProbs` 稳定在
  `[0.1~0.2, 0.8~0.9, 0.8~0.9, 0.2~0.3]`（左右邻车道线置信度 0.8+），与之前 PC 上
  验证通过时的数值量级一致

### 结论

**CPU 模式在 Orin NX 上完全可以稳定跑 demo.mp4 并产出正确的车道线预测**，不需要
GPU 加速才能用。之前"CPU 模式推理速度不足未能验证"的记录是因为没有意识到
`WEBCAM_FPS` 需要匹配实际处理能力，而不是 CPU 推理本身有问题。这也从另一个角度印证
了第九/十一节对 CUDA 路径瓶颈的判断方向——CPU 路径本身是健康、可用的，问题只出在
CUDA 路径的调度开销上，不是"CPU 太慢所以必须上 GPU"。

**生产部署（`start_openpilot_orinnx.sh`，真实摄像头场景）不受此问题影响**：真实
摄像头默认帧率通常和 `demo.mp4` 场景一致地用 `20fps`（`camerad.py` 中非视频文件
分支固定 `fps=20`，不受 `WEBCAM_FPS` 影响），仍然会远高于 CPU 处理能力，***如果
生产也要用 CPU 模式跑，需要专门评估 20fps 输入下 CPU 推理够不够，大概率不够，
这种场景才是 GPU 加速真正有意义的地方***。`WEBCAM_FPS` 环境变量本身只在
`camera.py`/`camerad.py` 判断 `cam.is_video_file` 为真时才生效，仅适用于
`demo.mp4` 这类视频文件回放验证场景。

### 待办

- 生产双摄像头场景（20fps 真实摄像头，非视频文件）下 CPU 模式能否达到可用帧率，
  尚未实测，需要在真实摄像头环境下专门验证（不能用 `WEBCAM_FPS` 缓解，因为该变量
  对非视频文件输入不生效）
- 如果实测证明 20fps 场景 CPU 确实不够用，则 GPU 加速（第九/十一节的 TICI 式
  一次性初始化修复方向）仍是必要的后续任务，不能因为本节发现而搁置

## 十三、CPU 模式接入真实摄像头验证（2026-07-10）：发现并修复两个阻断性 bug

### 结论：修复两个 bug 后，CPU 模式接入真实摄像头（20fps）已能稳定产出 modelV2

用 `SINGLE_CAM=1 DISPLAY=:0 ./start_openpilot_orinnx.sh` 在 Orin NX 上接入真实 USB
摄像头（非 demo.mp4）验证 CPU 模式，过程中发现并修复了两个此前从未在真实摄像头场景
下暴露过的阻断性问题（demo.mp4/PC 验证路径都绕开了这两个坑）。

### Bug 1（已修复并提交，`d7a835467`）：webcam 分辨率协商不一致导致 camerad 静默崩溃

**现象**：`SINGLE_CAM=1` 跑生产脚本，`webcamerad` 完全不出现在进程树里，manager 日志
毫无报错痕迹（UI 反复崩溃刷屏进一步掩盖了线索）。

**根因**：`tools/webcam/camera.py` 中，`read_frames()` 无条件把每一帧 resize 到
`target_W/target_H`（固定 1928×1208），但 `self.W/self.H`（摄像头模式下）用的是
`cap.get()` 协商后的**实际**分辨率。USB 摄像头驱动不支持精确的 1928×1208，实测
`v4l2-ctl` 列出的离散尺寸里最接近的是 1920×1080，`cv2.VideoCapture` 请求 1928×1208
后驱动会静默协商到 1920×1080：
```python
cap.set(CAP_PROP_FRAME_WIDTH, 1928.0)
cap.set(CAP_PROP_FRAME_HEIGHT, 1208.0)
cap.get(CAP_PROP_FRAME_WIDTH), cap.get(CAP_PROP_FRAME_HEIGHT)  # 实测: (1920.0, 1080.0)
```
`camerad.py` 用协商后的 `cam.W/cam.H`（1920×1080）给 VisionIPC `create_buffers`
分配缓冲区，但 `read_frames()` 产出的实际数据是 resize 后的 1928×1208，两者大小不
匹配，触发：
```
AssertionError: assert buf.len == len(data)
  (msgq_repo/msgq/visionipc/visionipc_pyx.pyx:83 in VisionIpcServer.send)
```
这个异常发生在 `camera_runner` 的独立线程内，未被捕获，导致该线程静默退出，
主进程还在（不报错、不重启），manager 那边看不到任何异常记录。

**修复**：`self.W/self.H` 改为始终使用 `target_W/target_H`（和 resize 目标保持一致），
不再用协商后可能不同的实际分辨率。已提交 `d7a835467`。

**排查方法记录**：manager 日志因 UI 崩溃循环刷屏、且线程内异常不会传播到父进程日志，
两层掩盖导致无法从常规日志定位。最终靠 `USE_WEBCAM=1 python3 -m tools.webcam.camerad`
手动单独跑该模块，才在终端直接看到真实的异常堆栈。**排查生产脚本里"某进程完全不在
进程树里、日志也没有任何报错"的情况时，跳过 manager 包装、直接手动跑该模块的
`main()` 往往是最快的定位方式**。

### Bug 2（已定位，未修复，当前用手动注入绕过验证）：无 panda 场景下 `card` 永久阻塞，`modeld` 因此永久卡住

**现象**：修复 Bug 1 后 `webcamerad` 正常运行，`roadCameraState` 稳定产出（301帧/15秒，
约20fps），但 `modelV2` 仍然是 0。

**根因**：`selfdrive/car/card.py` 的 `Car.__init__` 里：
```python
if CI is None:
  print("Waiting for CAN messages...")
  while True:
    can = messaging.recv_one_retry(self.can_sock)
    if len(can.can) > 0:
      break
```
`card` 无条件阻塞等待第一条**真实 CAN 消息**才会继续往下走（包括写入 `CarParams`）。
本项目场景是 `NOBOARD=1`（无真实 panda 硬件），`pandad` 因此一直 `No pandas found`，
从未发出任何 `can` 消息，`card` 永久卡在这一步。而 `selfdrive/modeld/modeld.py` 的
`CP = messaging.log_from_bytes(params.get("CarParams", block=True), car.CarParams)`
是阻塞等待 `card` 写入 `CarParams`，`card` 卡住 → `modeld` 跟着永久卡住 → 从不进入
主推理循环 → `modelV2` 永远是 0。这与 `FINGERPRINT` 环境变量无关——`FINGERPRINT`
只在拿到第一条 CAN 消息**之后**的车型识别阶段才生效，在此之前的等待环节完全不受影响。

这正是 `learn-docs/车型适配/Orin_NX_部署指南.md` "发现4" 记录过的风险点，此前只是
理论分析，**本次是首次实机复现并确认必然触发**（因为 `NOBOARD=1` + 无真实硬件是
本项目当前固定配置，不是偶发条件）。

**验证性绕过**（非正式修复，仅用于确认这是唯一剩余阻断点）：手动执行等价于
`run_laneline_demo.py` 里 `setup_params()` 的操作——
```python
from openpilot.common.params import Params
from cereal import car
CP = car.CarParams(notCar=True, wheelbase=2.631, steerRatio=15.6)
Params().put("CarParams", CP.to_bytes())
```
在 `card`/`modeld` 已经处于阻塞状态时手动跑这段代码，`modeld` 立即解除阻塞进入主
循环，**同一次会话里 15 秒内稳定收到 50 帧 `modelV2`**（`roadCameraState` 301帧，
説明 20fps 输入下 CPU 模式确实能持续产出结果，不是像 demo.mp4 场景那样被
`prepare_only` 追帧机制完全堵死——真实摄像头场景下的丢帧模式和视频文件回放场景
不同，可能与两者的时间戳/节奏特性差异有关，值得后续关注但不影响本次结论）。

laneLineProbs 数值接近 0（测试环境是室内、镜头没对着真实车道线），这是预期现象，
不代表推理链路本身有问题——链路本身（webcamerad → VisionIPC → modeld → modelV2）
已跑通。

### 结论回答用户问题：CPU 模式接入真实摄像头是可行的，但生产脚本需要修复 card 阻塞问题才能独立运行

### Bug 2 正式修复（2026-07-10，已实现于 `start_openpilot_orinnx.sh`，待实机验证）

采用"注入方案"落地，**未改 `card.py`**。实现中发现并绕过了一个关键时序坑，记录如下。

**时序坑：pre-manager 预写 CarParams 会被 manager 清除。** 最初想在脚本"跳过
onboarding"的 python 块里直接 `put("CarParams")`，但 `CarParams` 的参数标志是
`CLEAR_ON_MANAGER_START | CLEAR_ON_ONROAD_TRANSITION`（`common/params_keys.h:23`），
`manager_init()` 启动时清一次（`manager.py:46-47`）、offroad→onroad 转换时再清一次
（`manager.py:199`），且 `IsOnroad=True` 在同轮清除**之后**才置位。所以脚本在 manager
之前写的 CarParams 一定被清掉。第十三节手动注入能成功，正是因为它在 card/modeld 已
跑起来并卡住（即 onroad 清除点之后）才注入。

**最终实现：后台看门狗注入器。** 在 `exec ./launch_openpilot.sh` 前台拉起 manager
之前，后台起一个 python 看门狗：只要 `CarParams` 缺失就补写
`car.CarParams(notCar=True, wheelbase=2.731, steerRatio=15.6)`，直到它连续稳定存在
10 秒才判定已越过所有清除点并退出（硬上限 180 秒防孤儿进程）。

**为什么不用 `IsOnroad` 做闸门（实机验证才暴露的坑）**：最初设计成"等
`IsOnroad=True` 再注入"，但在 hal9000 实测发现 `IsOnroad` 会残留上次运行的 stale
`True`（关机不清除）——当时没有任何 manager 在跑，`p.get_bool("IsOnroad")` 却返回
`True`。若据此判断，注入器会在 manager 启动前就注入，随后被 `manager_init` 清掉，
而固定的守护窗口若在 manager 完全起来前耗尽就会漏掉最后一次清除。改成看门狗后不
依赖任何 onroad 信号，只以"CarParams 稳定存在"为准，对 stale 状态和多次清除都健壮。

**为什么天然只读、不用改 card.py**：`card` 无 CAN 会一直阻塞在等 CAN，永远不置
`ControlsReady=True`；而 `pandad` 的 `setSafetyMode()` 依赖 `ControlsReady`
（`panda_safety.cc:fetchCarParams`）才执行，故 panda 一直停在上电默认只读态
（SILENT/NO_OUTPUT）。注入器仅在 `CarParams` 缺失时写，若真车 CAN 接入、card 正常
识别并写入，注入器不会覆盖，行为安全。

**参数选择**：`notCar=True` 是第十三节已验证可行的最简方式（与 `run_laneline_demo.py`
一致），wheelbase 用速腾正式值 2.731。后续需要更完整车辆几何时可改注入
`CarInterface.get_non_essential_params(CAR.VOLKSWAGEN_SAGITAR_MK7)`。

**验证状态**：bash 语法、内嵌 python 均 py_compile 通过；**实机端到端（起车后 onroad
→ 注入 → modeld 出 modelV2）尚未在 Orin NX 验证**，需现场确认注入器时序与 modeld
解阻塞。

## 十四、模型真实输入分辨率排查：512×256 已是固定小尺寸，非可调优化项（2026-07-10）

### 问题背景

第十三节确认 CPU 模式能在真实摄像头（20fps）下跑通后，产生一个新思路：既然摄像头
采集的是 1928×1208 大图，是否可以直接用更小尺寸的摄像头输入，从而减少预处理/传输
开销、加快整体推理速度？带着这个问题排查了 openpilot 官方架构和本仓库代码，结论是
**这个优化空间已经被官方架构本身用掉了，摄像头大图与模型输入分辨率之间本来就是解耦
的两件事，模型输入早就是固定小尺寸（512×256），不是可调参数**。

### 官方摄像头分辨率 vs 模型真实输入分辨率

- **comma 官方硬件（comma 3/3X）摄像头采集**：road camera（fcam）与 wide camera
  （ecam）均为 **1928×1208**（16MP 传感器降采样后的处理分辨率），这也是本仓库
  `ROAD_CAM_INTRINSICS`/`ROAD_CAM_SIZE` 默认值 1928×1208 的来源。
- **模型真实输入分辨率**：**512×256**（宽×高），YUV420 格式，硬编码在
  `selfdrive/modeld/models/commonmodel.h`：
  ```cpp
  class DrivingModelFrame : public ModelFrame {
    const int MODEL_WIDTH = 512;
    const int MODEL_HEIGHT = 256;
    const int MODEL_FRAME_SIZE = MODEL_WIDTH * MODEL_HEIGHT * 3 / 2;
    const int buf_size = MODEL_FRAME_SIZE * 2; // 两帧temporal skip
  };
  ```
  实测本仓库 pkl 元数据核对一致：
  ```python
  # driving_vision_metadata.pkl
  input_shapes: {'img': (1, 12, 128, 256), 'big_img': (1, 12, 128, 256)}
  ```
  （12 通道 = 两帧 × 6 通道 YUV420；128 是 YUV420 半高存储格式下的行数，对应实际
  图像分辨率即 512×256）。外部社区复现项目（[openpilot-pipeline](https://github.com/nikebless/openpilot-pipeline)）
  的描述与此一致：模型输入是两帧连续画面转 YUV420 堆叠成 `(N,12,128,256)` 张量。

### 数据流：大图与模型输入之间有一步 GPU 变换，完全解耦

```
摄像头原始采集 (1928×1208，或本项目 USB 摄像头协商后的 1920×1080)
    ↓  VisionIPC 传输大图（camerad → modeld）
    ↓  GPU/OpenCL warpPerspective（selfdrive/modeld/transforms/transform.cl）
       一步完成透视投影 + 缩放，直接输出模型尺寸
模型真实输入 (512×256)  ←  这一步已经是"小尺寸"，且是固定值
    ↓
driving_vision 模型推理
```

关键代码路径：`ModelFrame::prepare()`（`commonmodel.h`）调用
`run_transform()` → `transform_queue()`（`transform.cl` 的 `warpPerspective` kernel），
用标定矩阵 `projection`（即 `get_warp_matrix()` 算出的透视变换矩阵）把任意分辨率的
输入图像直接投影+缩放到 `MODEL_WIDTH × MODEL_HEIGHT`。这一步在 GPU 上做，输入图像
分辨率大小基本不影响这步的相对耗时占比。

### 结论：不存在"用更小图像输入加快推理"这个优化空间

1. **512×256 不是运行时可调参数，是训练时代码写死的模型架构约束**。onnx 计算图
   本身按此尺寸构建，改分辨率会直接导致输入 shape 不匹配报错，除非重新训练模型。
2. **"用小尺寸摄像头输入"这个思路在架构层面已经被实现了**——不是通过换小分辨率
   摄像头，而是通过 GPU warp 变换把任意输入分辨率都归一化到固定的 512×256 再喂
   给模型。摄像头端用 1928×1208 大图不是浪费，反而是为了给这一步 warp 变换提供
   足够的分辨率余量（数字变焦/透视校正需要原始细节）。
3. **CPU 推理 233ms/帧慢的瓶颈不在预处理图像尺寸**，模型输入本来就只有 512×256
   这么小。真正的耗时是模型本身的计算量（卷积层数/参数量固定）和 tinygrad
   的调度开销（详见第九/十一节 CUDA 路径的 `topovisit`/`graph_rewrite` 分析），
   与摄像头采集分辨率无关。
4. 因此，"减小输入图像尺寸来提速"这条路径在当前模型架构下**不可行**，也没有必要
   ——architecture 已经用 GPU warp 变换解决了这个问题。真正值得投入的提速方向仍是
   第九/十一节定位的两个方向：CUDA 路径的一次性初始化改造，或接受 CPU 模式但控制
   好喂帧速率（第十二/十三节已验证可行）。

## 十五、CarParams 注入方案设计中发现的安全风险：card.py 会自行重算 passive，PASSIVE 环境变量是摆设（2026-07-10，暂停实施，待确认）

### 背景

第十三节记录了 Bug 2（`card` 因 `NOBOARD=1` 下永久等不到真实 CAN 消息而卡死，
`modeld` 连带卡住），当时用手动注入 `CarParams` 验证过绕过可行，计划正式实现为
启动脚本里的固定注入逻辑。设计方案时，用 CodeGraph 追踪 `card.py` 的完整初始化
链路和 `PASSIVE` 环境变量的实际使用情况，发现了一个必须先确认清楚、不能直接实现
的安全问题，**本节记录发现，实施本身已暂停**。

### 发现 1：`card.py` 不是"写入 CarParams 就完事"，它会自己重新计算 `passive`

`selfdrive/car/card.py` 的 `Car.__init__` 里，不管 `CarParams.passive` 传入时是什么
值，都会执行：
```python
self.CP.alternativeExperience = 0
openpilot_enabled_toggle = self.params.get_bool("OpenpilotEnabledToggle")
controller_available = self.CI.CC is not None and openpilot_enabled_toggle and not self.CP.dashcamOnly
self.CP.passive = not controller_available or self.CP.dashcamOnly
```
`OpenpilotEnabledToggle` 这个 Param 在 `common/params_keys.h` 里**默认值是 `"1"`**
（即默认开启）。本地实测 `VOLKSWAGEN_SAGITAR_MK7` 的真实 `CarParams`（用
`CarInterface.get_non_essential_params(CAR.VOLKSWAGEN_SAGITAR_MK7)`）：
```
brand: volkswagen
carFingerprint: VOLKSWAGEN_SAGITAR_MK7
mass: 1536.0
wheelbase: 2.7309999465942383
steerRatio: 15.600000381469727
networkLocation: fwdCamera
notCar: False
dashcamOnly: False
openpilotLongitudinalControl: False
radarUnavailable: True
```
`dashcamOnly=False`、`notCar=False`，且 `self.CI.CC`（`CarController` 实例）在
`CarInterfaceBase.__init__` 里无条件创建，不是 `None`。**这意味着如果让 `card.py`
走到这一步正常跑完，`controller_available` 会被算成 `True`，`self.CP.passive` 会被
强制覆盖为 `False`**——不管注入 `CarParams` 时想让它是什么值。`passive=False` 之后，
`step()` 主循环会调用 `controls_update()` → `self.CI.apply()` 生成真实转向/加速的
CAN 消息，经 `pandad` 发往 CAN 总线。

### 发现 2：`PASSIVE` 环境变量当前是摆设，没有任何代码路径读取它

全仓库搜索 `os.environ.get('PASSIVE'`、`os.getenv('PASSIVE'` 等模式，唯一命中是
`run_laneline_demo.py` 里的 `os.environ['PASSIVE'] = '1'`——**这只是"设置"这个变量，
没有任何代码在"读取"它**。`start_openpilot_orinnx.sh` 里 `export PASSIVE=1` 同理，
写了但没人读。真正决定 `passive` 状态的是上面发现 1 里 `card.py` 内部重算的逻辑，
和 `OpenpilotEnabledToggle`/`dashcamOnly`/`CI.CC is None` 这三个条件，与 `PASSIVE`
环境变量完全无关。**当前启动脚本里 `PASSIVE=1` 这行给人"已经设置了被动模式"的错觉，
实际没有任何保护作用。**

### 发现 3：`pandad` 不受 `NOBOARD=1` 影响，一直在运行

`system/manager/manager.py` 的 `manager_thread()` 里：
```python
if os.getenv("NOBOARD") is not None:
  #ignore.append("pandad")
  print("\033[33m[MANAGER]\033[0m 💻 PC模式，忽略硬件进程: pandad")
```
`ignore.append("pandad")` 这行**被注释掉了**，只是打印了一行提示，`pandad` 实际
仍在 `always_run` 条件下正常启动。结合前面装车记录（`lsusb` 确认识别到真实
comma panda 硬件，通过 USB 物理接入），这意味着：**当前架构下 `pandad` 一直在
运行、一直能力上能向 CAN 总线发送**，唯一的保护层是 panda 固件内部的安全模式
（`SafetyModel`）状态，而不是 openpilot 侧的 `NOBOARD`/`PASSIVE` 这些"看起来像是
开关"的环境变量。

### 结论：CarParams 注入方案不能只关注"解除 card 阻塞"，必须同时保证 passive 不被覆盖

正式实现第十三节的 Bug 2 修复前，除了写入车型正确的 `CarParams`，**还必须显式
处理 `OpenpilotEnabledToggle`**（比如强制置为 `False`），或者在更靠近安全边界的
地方加一道不依赖这个 Toggle 的、明确无法被绕过的闸门，否则"注入 CarParams 解除
阻塞"这个改动本身就可能在无意中把系统从"纯只读观察"切换成"会真的往 CAN 发送
控制指令"的状态——这已经超出"车道线预测不控车"的当前项目目标范围，风险等级高，
**在没有确认清楚以下几点前不会继续实施**：

1. 今天实车测试时 panda 是否物理接入了车辆的 CAN harness（真实接线，还是只是插着
   USB 但没接车）
2. 今天测试过程中 `card`/`pandad` 是否已经跑起来过，过程中有没有观察到任何车辆
   报警/异常（这是理解当前实际风险状态的关键背景，不能凭空设计后续方案）
3. 正确的"永久保持只读/不控车"防线应该设在哪一层——是每次启动脚本里显式设置
   `OpenpilotEnabledToggle=False`，还是需要更底层、更难被绕过的保护（比如确认
   panda 固件当前的 `SafetyModel` 实际状态，需要用 `panda.health()` 现场核实）

- 本节仅为方案设计阶段的风险记录，供确认清楚后继续第十三节 Bug 2 的正式修复

### 只读防线方案（双保险，供审阅，尚未实施）

> 本小节是在上面风险分析基础上设计的最小防护方案，**仍未落地**，等三个待确认项
> 坐实后再实施。设计原则：不依赖会被 `card` 重算的 `passive`，也不依赖没人读取的
> `PASSIVE` 环境变量，而是去拨动真正决定 `controller_available` 的杠杆
> （`OpenpilotEnabledToggle`），并在 panda 固件层做一次独立核实。两道闸门都收敛到
> 同一终态：panda 固件安全模式 = `noOutput`（TX 被固件拒绝）。

#### 第一道：软件闸门 —— 启动前强制 `OpenpilotEnabledToggle=False`

在 `start_openpilot_orinnx.sh`（及 `start_openpilot.sh`）拉起 manager **之前**插一行：

```bash
# 只读防线：强制关闭 openpilot 控车总开关，使 card 重算出 passive=True
python3 -c "from openpilot.common.params import Params; Params().put_bool('OpenpilotEnabledToggle', False)"
```

生效链（均已在代码中核实）：

```
OpenpilotEnabledToggle=False
      │  card.py:114  openpilot_enabled_toggle=False
      ▼
controller_available = False           (CI.CC 非 None、dashcamOnly=False 都不再重要)
      │  card.py:115
      ▼
self.CP.passive = True
      ├─ card.py:116-119  safetyConfigs=[noOutput] ─▶ 写入 "CarParams" 参数
      │                                              ─▶ pandad setSafetyMode() 把物理 panda 设成 noOutput
      └─ card.py:250      not passive == False，step() 不再调 controls_update()/CI.apply()
```

一处设置，openpilot 侧（不生成控制 CAN）与 panda 固件侧（不放行 TX）**同时**落到
只读态。对车道预测无副作用：`passive=True` 只让 `selfdrived` 走
`startupNoControl`/`dashcamMode`（`selfdrived.py:131-140`），不影响 modeld/UI，
车道线照常显示。

注意点：
- `OpenpilotEnabledToggle` 是 `PERSISTENT` 参数（`common/params_keys.h:103`，默认 `"1"`），
  设一次会留存；但 UI 上的开关仍可能把它扳回，锁定部署可接受，需知悉。
- 该行须在 manager 启动前、params 目录已就绪时执行。

#### 第二道：硬件闸门核实 —— `panda.health()` 现场断言

不依赖软件推断，起车后跑独立脚本直接问 panda 固件当前安全模式，放行前人工确认：

```python
#!/usr/bin/env python3
# tools/vw/check_panda_readonly.py —— 核实 panda 固件处于只读安全模式
from panda import Panda

SILENT, NO_OUTPUT = 0, 19  # car.capnp SafetyModel: silent@0, noOutput@19

p = Panda()
h = p.health()
mode = h["safety_mode"]
allowed = mode in (SILENT, NO_OUTPUT)
print(f"safety_mode={mode}  controls_allowed={h['controls_allowed']}  -> {'只读 OK' if allowed else '⚠️ 可能可写!'}")
assert allowed, f"panda 安全模式={mode}，不是 silent/noOutput，禁止上路观察"
assert h["controls_allowed"] == 0, "controls_allowed 非 0，panda 认为可以下发控制"
```

`safety_mode`/`controls_allowed` 字段来自 `panda/python/__init__.py:516-518` 的 health 包，
两者都为只读态才放行。

## 十六、摄像头升级调研：海康威视 C6 Lite 不可行，结论是换 UVC 模组或走真正的 RTSP IPC（2026-07-10，暂停，待后续考虑）

### 背景

当前 USB 摄像头画质有限（第七节记录过强光/暗光曝光问题）。调研能否用海康威视
C6 Lite（消费级行车记录仪，2K）替代，作为提升画质的手段。

### 结论：C6 Lite 这条路不可行，暂不投入

C6 系列（含 C6 Lite）是消费级行车记录仪，与海康专业网络摄像机（IPC）产品线完全
不同：

- **无标准视频接口**：只有 Wi-Fi 热点 + 手机 App（HikDashcam/hiDashCam）预览/回放，
  **没有 RTSP、没有 ONVIF、没有 UVC**。机身 MicroUSB 口官方说明是"可扩展 GPS 或
  4G 接口"，不是 USB Video Class 视频输出口，插电脑不会被识别成摄像头。
- **协议未公开**：手机 App 与设备之间走海康自家私有 P2P/局域网协议，无公开文档、
  无第三方 SDK，也没找到针对海康消费级行车记录仪的公开逆向成果（对比小米/70mai
  等消费级摄像头，社区有逆向先例，如
  [70mai M300 Toolbox](https://github.com/XuZhen86/70MaiM300Toolbox)、
  [Xiaomi Camera Hack](https://github.com/hatsujouki/xiaomi-camera-MJSXJ09CM-hack)，
  但海康这款没有）。

评估过三条路径：
1. **逆向 Wi-Fi 私有协议自己写客户端**：无公开资料可参考，需要完整抓包分析认证/
   流协商/可能的加密，工作量大且结果不确定，固件更新还可能使其失效，不建议。
2. **拆机取传感器模组另配 UVC 采集板**：需要传感器型号/时序协议/FPC 定义，消费级
   产品通常不公开，拆解有损坏风险，性价比差，不建议。
3. **换成真正带标准接口的摄像头**（推荐方向，见下）。

### 推荐方向：换 UVC 模组，或换海康专业 IPC + RTSP

`tools/webcam/camera.py` 当前走 `cv2.VideoCapture(camera_id)`，两种方案改动都很小：

- **换更好的 UVC USB 摄像头模组**（改动量：零）：`camera_id` 传设备号/路径，代码
  完全不用改，只需选购画质更好（宽动态范围、合适帧率）的 UVC 模组。
- **换海康专业网络摄像机（IPC）+ RTSP**（改动量：小）：`cv2.VideoCapture` 原生支持
  `rtsp://user:pass@ip:554/...` 字符串。`camera.py` 里 `is_video_file` 判断
  （`os.path.isfile`）需要加一个"URL 是否为 `rtsp://` 前缀"的分支跳过文件检查，
  其余流程不变。权衡：RTSP 走 Wi-Fi/网络会引入额外延迟抖动，且要求摄像头和 Orin
  NX 同局域网，工程稳定性不如 UVC 直连。

### 当前状态

**暂停，后续再考虑**。未做任何代码改动，也未采购硬件。若后续要推进，优先方向是
选购更好的 UVC 模组（零代码改动，风险最低）；RTSP IPC 方案作为备选，需要先确认
是否有可用的专业 IPC 设备。
